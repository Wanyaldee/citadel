# Contributing to Citadel

Thank you for your interest in improving Citadel!

Citadel is an independent, non-commercial fork of [Zed](https://github.com/zed-industries/zed), reworked into an IDE dedicated to Arduino (AVR) embedded development. It is not affiliated with Zed Industries, Inc. — see [legal/NOTICE.md](./legal/NOTICE.md).

All activity in this repository is subject to our [Code of Conduct](./CODE_OF_CONDUCT.md).

Because this is a small, independent fork (not a company-backed project), there is no CLA to sign and no dedicated support team — reviews happen as maintainer time allows.

## Contribution ideas

Citadel's focus is narrower than upstream Zed: making the Rust/C boundary (see [README.md](./README.md#architecture-the-rustc-boundary)) and the Arduino/AVR workflow solid, not general-purpose editor features.

**We love PRs that are**:

- Fixing or extending the **embedded-specific docs** (serial monitor/plotter, `citadel init`, build/flash pipeline).
- Fixing **bugs** in the Arduino/AVR toolchain integration (serial I/O, build, flashing) or in the Rust/C boundary checker.
- **Small** enhancements that make the embedded workflow work for more boards/platforms.
- Anything tracked in [tasks/todo.md](./tasks/todo.md) or the [RFCs](./docs/rfcs/).

If you're proposing a larger feature (especially anything touching the Rust/C boundary rules described in [RFC 0001](./docs/rfcs/0001-hybrid-architecture.md) or [RFC 0002](./docs/rfcs/0002-product-scope-and-dx.md)), open a GitHub discussion or issue first rather than starting with a PR — this avoids wasted effort on work that doesn't fit the project's scope.

A Citadel Discord server is planned; once it's up, it will be an additional place to discuss ideas and proposals informally before writing them up as a GitHub discussion or issue. The link will be added here when it's live.

## Language

Write all commit messages, code comments, PR descriptions/discussion, and documentation in **English**, even if you're more comfortable in another language. This keeps the project's history and docs consistent and readable for every contributor, maintainer included (see the [Code of Conduct](./CODE_OF_CONDUCT.md) — nobody here is a native speaker either). If English isn't your first language, a machine-translated draft is fine; just make sure it reads clearly.

This also applies to anything the IDE itself says to the user: diagnostics, error messages, log output, UI strings. Zed and Microchip Studio are both English-first, and so is Citadel — don't add localized user-facing strings. (The boundary-lint prototype's Japanese diagnostic messages predate this rule and should be translated to English as part of any further work on it.)

Maybe if Citadel ever gets big enough to justify it, we'll revisit localization someday — but that's a "someday" problem, not a "now" problem.

## Sending changes

Open a pull request against `main`. Please:

- Make sure the change is **desired**: for anything beyond a bugfix, check [tasks/todo.md](./tasks/todo.md) and existing issues, or open a discussion first.
- Include a clear description of **what you're solving**, and why.
- Include **tests** where practical. For hardware-dependent behavior that can't be unit tested, describe how you verified it on real hardware (board, sketch, steps).
- If the change is visible in the UI, attach **screenshots or screen recordings**.
- Make the PR about **one thing only**.
- Keep AI assistance under your judgement and responsibility: don't submit a PR generated by an AI that you don't understand and can't explain.

## Things we will (probably) not merge

- Changes to the Rust/C boundary enforcement that weaken the "no logic in C/C++" rule without a corresponding RFC discussion.
- General-purpose editor features unrelated to the embedded/Arduino workflow — those belong upstream in [Zed](https://github.com/zed-industries/zed) itself.
- Non-trivial changes with no tests and no hardware verification notes.
- Anything that seems AI-generated without understanding the output.

### AI Policy

We welcome the use of LLMs for coding, but we expect a human in the loop who genuinely understands the work an LLM produces on their behalf. We don't accept contributions from autonomous agents submitted without review. Pull requests that appear to violate this may be closed without notice.

If you share context from a chat with an LLM in a PR description or comment, put the relevant part in a quote block, disclose it as AI-generated, and add your own commentary on why it's relevant.

This policy is adapted from [Zed's AI policy](https://github.com/zed-industries/zed/blob/main/CONTRIBUTING.md#ai-policy), itself adapted from [ripgrep's AI policy](https://github.com/BurntSushi/ripgrep/blob/f0cec341ab95c25c691ad3d5754d4bd9eedde21f/AI_POLICY.md).

## Bird's-eye view of Citadel

Citadel inherits Zed's crate structure; see [Zed's glossary](docs/src/development/glossary.md) for the terms used throughout the codebase. Crates specific to Citadel's embedded focus:

- [`citadel_new_project`](/crates/citadel_new_project) handles Arduino/AVR project scaffolding (`citadel init`).
- [`citadel_serial_monitor`](/crates/citadel_serial_monitor) implements the serial monitor and serial plotter.
- [`citadel_build`](/crates/citadel_build) drives the split C/C++ + Rust build and the static link/flash pipeline described in the [README](./README.md#architecture-the-rustc-boundary).

For the rest of the codebase (`gpui`, `editor`, `project`, `workspace`, `lsp`, `language`, `theme`, `ui`, `cli`, `zed`), see [upstream Zed's CONTRIBUTING.md](https://github.com/zed-industries/zed/blob/main/CONTRIBUTING.md#birds-eye-view-of-zed) — those crates are largely unchanged from upstream.
